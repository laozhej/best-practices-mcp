# M4 — Optional project-keyed persistence

## Commitments

M4 added `read_draft` and `update_draft`, completing the nine-tool surface. Omitted documents resolve a complete stored snapshot; explicit documents, including `{}`, bypass storage. Stored mode in the reference host remains opt-in, and all persistence access goes through MCP.

## Findings and fixes

Review identified uncertain-write recovery that could suggest an unsafe retry after a committed update. Recovery now requires a fresh `read_draft` before deciding on another patch. The host clears cached artifacts after uncertain outcomes instead of presenting them as current, while known precommit rejections preserve prior artifacts.

A cleanup path could report failure after successful replacement. The temporary-file marker is now cleared immediately on commit, with no later cleanup syscall that falsely suggests rollback. Cancellation shielding covers both the SDK's AnyIO scope and direct asyncio cancellation, retaining the project guard until replacement or cleanup finishes.

The storage contract checks both document and complete prospective response budgets before replacement, validates source identity before patching, and preserves complete reads with diagnostics. One process-local guard per project protects disjoint patches without promising cross-process locking, arrival order or power-loss durability.

## Outcome and limits

Independent integration and maintainability review approved the corrections. Storage failure/cancellation cases, reference-host restart/resume, both draft-source modes and installed-server Inspector checks passed. The tool schemas and bounded scope were unchanged. Native platform/minimum-Python and independent application-host qualification remained M5 work; no BadgeApp authentication, browser execution or submission capability was introduced.
