# M6 — Publication preparation

## Commitments and settled decisions

M6 prepares the independent MIT-licensed Reponomics package for `reponomics/best-practices-mcp` and PyPI `best-practices-mcp`. The initial tag is `v0.1.0-beta.1` (Python package version `0.1.0b1`), followed by a separately built `0.1.0` release after successful published-package QA. Upstream notices and project-record attribution remain distinct from this project's license and non-affiliation statement.

The retained planning/review history lives under `docs/planning/initial-implementation/`; maintained specification, design, architecture and contracts are separate. Detailed QA reports and original records are preserved privately, while reusable tooling writes future reports under ignored `build/qa/`. The historical QA artifacts retained publicly are the approved live Chrome screenshots and their concise context, including the associated retained proposal URLs/script.

Release Please manages release PRs and lightweight tags using a scoped GitHub App token. Main-branch commits require signature verification; immutable GitHub releases protect published tags and attached assets. PyPI publication uses OIDC and a dedicated approval environment, with no PAT or long-lived PyPI token. The exact qualified wheel and sdist are uploaded without rebuilding in the privileged job. Their PyPI attestations are separate from GitHub release attestations.

## Extraction gate

The preserved development repository and its history remain intact. The clean repository starts with the exact empty commit message `Initial commit`, followed by a clean snapshot commit. Extraction requires the selected tree, license/notices, retained documentation, private archive verification, local checks and review to be concrete and free of unintended files. The cropped screenshot copies were visually approved; browser chrome and embedded metadata are removed from the public evidence.

The first snapshot need not be release-ready and is not assumed to be the commit published to PyPI. Subsequent commits in the new repository may activate CI, configure integrations, resolve findings and prepare the release. Remote service setup and actual publication qualification are later gates, not prerequisites for extracting the clean tree.

## Publication gate and remaining work

Before the first release, configure branch rules, the release App, Codecov, applicable code scanning, immutable releases, the `pypi` environment and the exact Trusted Publisher identity. Make the repository public before releasing, run the native matrix and release checks there, and review real integration results. A local configuration check or skipped job does not establish remote qualification.

After the beta is published, verify the README's production-PyPI `uvx` and `pipx` installation paths, installed CLI/version, real MCP discovery/calls and reference-host instructions using disposable storage. Hold stable publication while that verification fails, and correct or withdraw misleading installation guidance. Stable is a new qualified build and upload, not renamed beta archives.

M6 remains in progress. No clean-repository extraction or PyPI publication is claimed by this record. The [release procedure](../../../releasing.md) provides the maintained commands and setup details; generated QA reports record the current local evidence and pending manual gates.
