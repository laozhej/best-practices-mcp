Historical initial-implementation record. This preserves planning and review context, including the implementation status at its original checkpoints. Use the [maintained documentation](../../README.md) for current behavior. Detailed execution reports and earlier versions are archived privately; milestone summaries retain substantive findings and outcomes.

Updated 2026-11-10. M1 foundations, M2 public reads, M3 explicit document/validation/artifact operations and M4 optional persistence have been implemented. M5 CI, coverage, fresh-install and independent Codex desktop qualification passed; the optional-Ruby testing follow-up is recorded separately; the [M5 milestone summary](milestones/M5.md) tracks required acceptance evidence. The [M4 milestone summary](milestones/M4.md) records G4 verification and review; [M3 milestone summary](milestones/M3.md) record the completed owner-led form comparison. This plan replaces the earlier sequence that deferred contract choices until feature work. The [specification](badgeapp-mcp-spec.md) defines scope, the [contract addendum](badgeapp-mcp-contracts.md) fixes payloads and operational decisions, the [upstream baseline](badgeapp-mcp-upstream-baseline.md) identifies compatibility evidence, and the [readiness checklist](badgeapp-mcp-readiness.md) records review findings and approval. Approval here means the plan is ready for implementation, not that the unimplemented MCP or release has passed acceptance.

## Deliverables and boundaries

Deliver one independently installable local Python stdio MCP with exactly nine planned tools, packaged offline criteria, public BadgeApp reads, pure document/validation/artifact operations, and optional project-keyed storage. Deliver a separate small Python terminal reference host and deterministic tests, provenance, compatibility fixtures, and setup/use documentation. Each milestone also delivers a lightweight HTML owner-QA report with reproducible validation commands, as specified below.

The server owns BadgeApp mechanics shared by hosts: aliases, criteria interpretation, structural patch rules, public-read pacing/errors, transfer precedence and encoding, script guards, and atomic local storage. Hosts own project selection, evidence/reasoning, answer choice, selective explicit documents, override choice, artifact presentation/execution, repository publishing, and website saving. Do not add application policy to MCP handlers.

No new tools, resources, prompts, model providers, browser automation, authenticated writes, project creation, remote transport, registry, synchronization, batching, generator selectors, draft revision tokens, cross-process locks, or filtered draft reads. Optional validation never gates artifact generation. The originating Badge Buddy CLI is context, not a parity target. Reference-host conveniences do not become MCP requirements for every host.

Reopen scope only through an explicit design decision, never to make a failing test pass.

## Owner QA at every milestone

At each milestone, prepare a small standalone HTML document at `docs/qa/M0.html` through `docs/qa/M6.html`. These are development review artifacts, not MCP features or a hosted documentation product. Use a shared template and a small standard-library Python renderer; plain HTML/CSS is sufficient. No frontend framework, build service, external fonts/scripts, dashboard, or browser automation is required. Reports must open directly from disk, be readable on a normal laptop screen, and support printing. Commands appear as selectable text; report viewing never runs them.

Introduce this interface during M1 preparation, before completing feature work. At that point, prepare an M0 baseline report from the recorded planning/scaffold evidence, clearly identifying historical commands and their recorded environment rather than claiming a fresh run. This added reporting requirement does not retroactively withdraw G0 approval. M1 and every subsequent milestone must deliver its report before declaring its gate complete. M6's report documents release readiness and any actual publication authorization; report generation never publishes anything.

### Report contents

Keep the main report short enough for an owner to scan in a few minutes; use expandable details or links for longer evidence. Every report contains:

1. **Progress summary:** milestone/gate, a short description of what now works, what remains unimplemented, the tested implementation commit, dirty-worktree status, report generation time, test execution times, and interpreter/OS/SDK versions. Distinguish report freshness from evidence freshness. Link the previous milestone report and the relevant specification/plan sections.
2. **Commitment verification:** one row for each commitment in that milestone's gate, with status `passed`, `failed`, `not run`, or `not applicable`; the supporting command or manual check; observed result; and an evidence reference. Explain every not-applicable decision. Keep deferred/failed commitments visible rather than quietly removing them from the table. State overall gate status separately from individual test results.
3. **Decisions and changes:** list implementation decisions made since the previous milestone, reasons, affected contract/spec sections, and compatibility or scope implications. Distinguish routine implementation choices from changes requiring a design decision. Record reviewer disposition and whether owner input is needed. If none occurred, say so. Update the authoritative design documents when a decision changes them; the HTML is not an alternative specification.
4. **Owner verification:** three to five copyable steps, normally Make commands, with prerequisites, working directory, expected result, approximate duration, and any filesystem/network effects. Include one observable demonstration of the milestone's behavior and a relevant failure/edge case where available. Link sample inputs/output artifacts so the owner need not compose JSON or inspect test internals. Clearly label fixture-based checks, live reads, and manual host/platform checks.
5. **Open questions and next steps:** identify each unresolved issue, whether it blocks the gate, who should resolve it, the decision needed, and the recommended next action. Include known limitations and the next milestone's entry conditions. Explicitly state when no questions remain.
6. **Review status:** implementer completion, independent review findings/disposition, and owner feedback recorded separately. Use `not yet reviewed` unless actual owner feedback exists; automated test success and subagent approval are never labeled owner approval.

Evidence may be summarized inline or linked to small sanitized files under `docs/qa/evidence/Mn/`. Keep bulky transient logs in ignored build output; summarize their relevant results in the report. Do not include credentials, personal drafts, full sensitive proposal URLs, or local account-specific paths in committed reports. Use synthetic fixtures and repository-relative evidence links. HTML-escape all rendered values, including output excerpts. Commit the report and retained evidence; reports are not wheel runtime data. Include the template/renderer and reports in the sdist if needed to reproduce the development handoff.

### Simple validation interface

Add these annotated Make targets using the existing `PYTHON`/toolchain conventions during M1 preparation. The interface is implemented for M0–M4; later suites are added with their milestones:

| Command | Behavior |
| --- | --- |
| `make qa MILESTONE=M1` | Run the implemented offline verification suite mapped to that milestone and capture command, exit status, execution time, environment and concise results. Use temporary storage/test fixtures. Return nonzero for a failed required automated check, an unsupported milestone, or a required suite that has not been implemented; never substitute a successful placeholder. Manual checks remain explicitly not run until their evidence is recorded. |
| `make qa-report MILESTONE=M1` | Render/update `docs/qa/M1.html` from recorded evidence plus the implementer's short decisions/questions/summary record. Do not run tests or contact BadgeApp. Missing or stale evidence stays visible as not run/stale; rendering cannot mark the gate passed. |
| `make qa-open MILESTONE=M1` | Open an existing local report with the platform's default browser, or print its absolute file path when opening is unavailable. Do not rerun tests or modify evidence. |
| `make help` | List these commands and the underlying focused validation targets. |

Require an explicit supported `MILESTONE=M0` through `M6`; reject unknown values. A small JSON evidence/notes file per milestone is sufficient input to the renderer. Do not add a database, daemon, or general reporting framework. Retain the focused targets underneath the wrapper so failures are easy to reproduce independently. `qa` may run the same shared checks across milestones, but must not rerun all previous expensive manual or live checks by default.

### Milestone handoff procedure

Before closing a milestone: update its commitment table; run its implemented automated checks; record manual checks and omissions honestly; document decisions and open questions; render and inspect the HTML; obtain the milestone review; then refresh the report with the review outcome. If implementation changes after verification, mark affected evidence stale, rerun relevant checks, and regenerate before claiming the gate passed. Identify the tested implementation commit separately from a later documentation-only report commit to avoid a self-referential freshness requirement.

The completion message to the owner links the HTML and gives a short progress summary, significant decisions, open questions or their absence, and the few validation commands to try. Do not require the owner to reconstruct the result from chat history or raw logs. Owner review is facilitated at every milestone but is not a new mandatory approval pause for routine work: proceed under existing authorization when the technical gate is satisfied and no blocking decision remains. Respect an explicit request to stop for owner review, and retain the separate publication authorization at G6.

## Optional owner-led live QA after M3

After G3's deterministic checks and independent review pass, offer an owner-led check against the owner's current active BadgeApp application in their authenticated browser session. M3 is the appropriate first checkpoint because proposal URLs, exact overrides, scripts and the document-mode host are implemented then. M4 adds persistence and does not need to precede this form-transfer check; G5 should repeat a representative end-to-end scenario through the designated independent host. This is supplementary live compatibility evidence, separate from default offline QA and not a requirement to save a production form.

Prepare the M3 HTML report with a short live-QA worksheet, initially marked not run. Record the selected project/level, current public observation and actual form baseline, a small explicit proposal document, requested/effective overrides, and expected field-level outcomes before applying each artifact. The owner chooses the project and meaningful proposed changes and authenticates in the browser; the MCP continues to use public reads and return artifacts. Browser authentication, artifact application and any website saving remain host/user actions, with no credential transfer or new server capability.

Compare cases supported by that application's current state: filling eligible blank values; retaining existing values without overrides; replacing selected fields with explicit overrides; status overrides' inherited justification effects; and justification-only overrides blocked by a retained incompatible status. Check exact text/Unicode preservation and that unrelated fields remain unchanged. Evaluate each case from a fresh saved-form baseline so unsaved changes from another case do not contaminate the comparison. For a generated script, inspect its intended assignments before user/host execution and compare replacement behavior separately from URL override behavior. Wrong-target/disabled-control failures remain covered by controlled fixtures rather than deliberately damaging a live application.

Predictions cover documented edit-form behavior only. Do not model Save/Submit decisions or eventual persisted values. The upstream first-edit/reanalysis path may change form values before URL proposals, so compare the actual form baseline and classify discrepancies without implementing Chief or predicting its results. Begin with form inspection before saving. The owner can discard/reload the form or choose to save the reviewed intended changes; saving is not automatic or necessary for the initial comparison. If the owner saves, explicitly refresh public progress and compare the later saved observation, distinguishing saved state from merely populated form state. Record sanitized expected/observed outcomes and any deployment mismatch in the HTML report; keep full personal proposals and authenticated session data out of committed evidence. A live finding that contradicts an implementation claim reopens that claim for correction and relevant regression checks before dependent work relies on it.

## Concrete reference host

Extend `examples/host.py` as a deterministic terminal application using the official MCP client over a real server subprocess. It must not import `best_practices_mcp` domain modules, share private models, read server draft files directly, reimplement field/transfer rules, or require an LLM/account/model key. Keep the existing connection demonstration available as `--discover`; the normal application workflow is interactive once tools exist. `make example` remains a reproducible entry point.

Startup accepts `--server-command` (default installed executable), `--mode document|stored` (default document), and optional `--data-dir` absolute path passed only to the server environment. Each interaction session stores selected project/level in host memory only; it introduces no server session or registry. UI may suggest workflows but does not make validation compulsory. Display tool errors using their codes/recoveries; never retry a lost mutation automatically.

| Host action | Protocol use and observable behavior |
| --- | --- |
| Discover | List tools and verify required schemas/capabilities; fail clearly if connected to the scaffold or incompatible server. |
| Find/select | Prompt for query, show candidates with ID/URLs, allow next page when known or explicit next-page request when uncertain; require explicit selection even for one result. Verify a remembered ID with progress before a new workflow. With no match, show registration URL and permit fresh lookup; no draft work starts yet. |
| Choose level/view | Use get_criteria index and selected definitions; show get_project_progress summaries/answers, observation time and attribution. Do not label packaged wording necessarily current. |
| Create/import document | After project selection, create `{}` or load host-chosen JSON; call build_draft for normalization. Host memory is the document source, and export is the only host-owned persistence. No server data root is created. |
| Resume/create stored draft | After project selection, call read_draft or update_draft directly; a missing file offers an explicit first edit, not automatic creation. Show server location. Switching projects changes every call's project_id without restarting. |
| Edit/remove | Form a changes object using canonical fields from criteria plus the four metadata fields. Document mode calls build_draft; stored mode calls update_draft. Null removes locally. Display diagnostics/errors without changing successful-state indicators on failure. |
| Validate (optional) | Call validate_draft with selected level and explicit document or omitted draft; display checked/skipped scope and findings. Allow artifact generation regardless of findings or whether validation was called. |
| Prepare proposal | Call prepare_update_url; default no overrides. User chooses exact supplied fields to override, and host displays requested/effective scope and field-level predicted effects. An exceptional subset is a host-created explicit document; stored file remains untouched. |
| Prepare script | Call prepare_update_script; display replacement behavior, expected project/level and instructions. Save/copy exact JavaScript on request. Never execute it. |
| Export/open | Export full JSON document, exact URL string or JS to a user-chosen path. Stored-mode JSON export uses read_draft. Preserve UTF-8 characters and artifact bytes; a terminal host provides save-to-file as its portable exact-copy mechanism. URL opening is explicit host/user action; display/copy/open success is not website-save success. |
| Refresh | On request call get_project_progress again. Show observation independently from draft; do not synchronize automatically or claim that a generated artifact was saved. |
| Recover uncertain write | Explain uncertainty after lost response; call read_draft on request and let the user inspect before deciding on a new edit. No blind mutation retry. |

Reference-host validation uses a scripted input/output harness around the real MCP client/server and an injected test transport in the test server. No arbitrary upstream-origin flag is added to the production CLI. Fixture responses exercise deterministic branches; optional live reads are separate. The host may consume result objects as dictionaries and schemas dynamically, avoiding a second catalog or independently evolving domain model package.

## Required host acceptance scenarios

- [ ] Registered, unregistered, ambiguous and remembered-ID flows; user selection precedes draft work and registration remains external.
- [ ] Document mode: import/create/edit/optional validation, direct artifact generation without validation, exact export; absent/malformed stored file is irrelevant to an explicit document and storage root remains untouched.
- [ ] Stored mode: first edit without prior read, restart/resume, two projects in one server, default and override roots, complete-document export.
- [ ] Explicit `{}` and selective explicit document take precedence over existing stored data; no stored mutation occurs during generation.
- [ ] Incomplete, unchanged, unsupported-only, partial and entirely blocked transfer results are distinguishable; expected retained website values are not described as applied.
- [ ] Overrides display inherited justification effects; script warnings describe replacement and user save responsibility.
- [ ] Exact artifacts containing spaces, punctuation, quotes, Unicode and long explanations survive export/open plumbing byte-for-byte. Test actual artifact strings, not only rendered model links; do not impose a guessed URL budget.
- [ ] Invalid patch, missing file, project mismatch, rate limit, malformed upstream response and uncertain write outcome produce actionable UI states without false success.
- [ ] Explicit refresh shows saved observation separately and never merges it into the draft.

## Validation and packaging policy

Keep default tests offline. ### Schema design and compatibility checks

Carry the M2 JsonValue decision into M3–M5 and dependency changes. The [schema portability investigation](mcp-schema-portability.md#decision-and-sdk-support) records the official MCP SDK example/test of `Annotated[..., WithJsonSchema(...)]`, Pydantic's recommended annotation mechanism, specification guidance and measured Inspector results. The six-kind JsonValue declaration is this project's semantics-preserving use of that supported mechanism; do not describe it as a mandatory SDK recipe or treat the original empty schema as a protocol violation.

Use strict, concrete models for fields with known contracts. For the intentionally arbitrary JSON fields already specified—unfamiliar document values, error details, and preserved saved values—reuse the shared `models.JsonValue` annotation. Its `anyOf` admits null, Boolean, number (including integer), string, array and object; collection children remain arbitrary JSON. Keep the existing runtime validators and document/resource limits. Do not replace arbitrary JSON with object-only/string-only values, strip unknown data, alter null/omission semantics, or introduce per-tool schema rewrites merely to remove lint warnings.

For each milestone that exposes or changes a tool schema, and each SDK/Pydantic upgrade:

1. Review the declared contract first. Generate both input/validation and output/serialization schemas through the existing public model/adapter path, validate them as JSON Schema 2020-12, and inspect all affected snapshots. Explain any accepted-value change as a contract decision rather than an incidental lint fix.
2. Run `make test-contract`. Preserve the JsonValue semantic cases for scalars, null, nested collections, unfamiliar fields, error details and saved values; preserve runtime rejection of non-JSON/over-budget data and success/error output-schema checks. Add cases when a newly implemented path exercises a previously unverified use of these fields.
3. Run the pinned Inspector discovery command below against the implemented tool surface. Record Inspector/SDK/Pydantic/Node versions, tool count and exact findings in that milestone's HTML report and sanitized evidence. Inspector currently reports zero findings; review every new finding against the specification and intended contract. A legal construct may be retained with an explicit evidence-based reviewer disposition. Never narrow a correct contract only to obtain zero warnings.
4. Exercise each newly exposed or changed tool through Inspector using synthetic inputs and the milestone's fixture server; cover at least one successful result and a structured error, inspect text/structured content, and use temporary roots for mutation paths. This is development verification of the existing tools, not a production write or a new MCP capability.
5. Keep standards validity, schema/runtime agreement, Inspector lint and actual target-host behavior separate in the report. Invalid declared schemas, incorrect schema/runtime contracts, and failures of the milestone's required host scenarios block its gate. Unexplained Inspector findings remain unresolved review work; a warning is not automatically a specification violation. G5 still requires the independent application-host workflow.

```sh
npx -y @modelcontextprotocol/inspector@2.14.0 --cli \
  ./venv/bin/bestpractices-mcp --protocol-era modern \
```

Inspector is a development check with an explicit version pin, not a runtime dependency or a download inside default offline `make qa`. Use a compatible Node 24 release managed by nvm (24.22.1 satisfies the current pin). Keep Inspector installation/download and live network effects visible in owner commands. Revisit the pin deliberately with compatibility evidence; no Inspector warning justifies silently upgrading the runtime SDK.
