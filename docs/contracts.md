# V1 implementation contract

The [specification](specification.md) defines scope and tool inputs; this document defines exact result payloads, operational policies and edge cases for the implemented nine-tool server. Compatibility discrepancies require review before changing the contract.

## Common conventions

Use snake_case domain properties and strict JSON types. Objects below list their required properties; nullable properties are present as `null`. Reject extra tool arguments. SDK-generated input/output JSON Schemas are implementation deliverables, generated from these definitions and checked by fixtures. Do not introduce a second handwritten protocol implementation. Each successful payload is an object with `schema_version: 1`; JSON text content carries the same payload for clients without structured-content support. SDK wire names remain unchanged.

`project_id` is an integer greater than zero (not a Boolean, float, or numeric string); storage uses its decimal representation. `level` is one of `passing`, `silver`, `gold`, `baseline-1`, `baseline-2`, `baseline-3`. `criterion_ids`, when supplied, is an array of distinct canonical IDs; `[]` selects none, omission selects all, and a filter without a level is invalid. Unknown IDs for the selected level are errors, including an ID valid only at another level. Arrays of result fields/criteria use canonical lexical order, except project candidates, which preserve upstream order. No selection is inferred from the first search result.

Optional arguments may be omitted but never set to `null`. In particular, use a distinct internal omission sentinel for `draft`; do not implement omission as `draft or read_file()`. `{}` is a valid explicit draft. `changes` is a JSON object; null is allowed only as a property value indicating removal. `build_draft` defaults `changes` to `{}`; `update_draft` requires it. An empty update to an absent draft creates `{}` as an explicit write. Empty updates to an existing valid draft need not rewrite it.

`Draft` is a flat map with string keys and JSON values. Published arbitrary-JSON fields explicitly enumerate null, Boolean, number, string, array and object with `anyOf`; collection children remain arbitrary JSON. This is schema-description guidance, not an object-only restriction or a change to runtime validation. See the [schema compatibility](schema-compatibility.md). Preserve unfamiliar JSON values, including nested objects/arrays, without interpreting them. Reject non-finite numbers, invalid Unicode, duplicate JSON keys in file/import bytes, non-object roots, and alias conflicts. MCP has already decoded tool input; the server cannot promise to detect duplicate keys erased by the protocol decoder. Aliases and canonical fields with identical values collapse to one canonical field; different values are `invalid_document`. Do not infer aliases by punctuation or case. Normalize against the pinned catalog alias map only.

Recognized status and justification fields and the four metadata fields are writable. All non-null patch assignments to unfamiliar or provenance fields (`id`, `repo_url`) fail, even if the field already exists. Null can remove any named field, including an absent or unfamiliar one. Conflicting aliases inside a patch fail before mutation; normalize the base and patch separately, then apply canonical keys. Thus a patch through an alias can intentionally replace a base canonical value. A recognized invalid base value can be repaired by a patch before structural validation. Invalid JSON or conflicting aliases cannot be repaired through a patch.

## Shared result types

| Type | Required properties and meaning |
| --- | --- |
| `CatalogRef` | `revision: string` (full upstream commit), `source_url: string`, `generated_at: string` (UTC RFC3339), `format_version: 1`. |
| `Observation` | `project_id: integer`, `source_url: string` (actual public JSON request), `fetched_at: string` (UTC RFC3339 after successful body receipt), `attribution: string|null`, `license: string|null` (upstream project-entry fields). |
| `Project` | `project_id: integer`, `name: string|null`, `repo_url: string|null`, `homepage_url: string|null`; absence is null here, never an invented answer. |
| `DraftSource` | `kind: "explicit"|"stored"`, `location: string|null`; absolute server path only for stored source. |
| `StructuralIssue` | `field: string`, `code: "unknown_field"|"invalid_type"|"invalid_status"`, `message: string`; diagnostics never include a copy of the field value. |
| `Identity` | `association: "storage_key"|"document_provenance"|"explicit_target"`, `id_check: "matched"|"absent"`, `repo_check: "matched"|"absent"|"not_checked"`. Storage-key association takes precedence, then explicit-document provenance, then caller target. This is association, not authentication. |
| `Error` | `code: string`, `message: string`, `details: object` (field/path/ID/status/limit as applicable, no answer bodies), `recovery: string`, `retry_after_seconds: integer|null`. |

Application failures return `{schema_version: 1, error: Error}` in an SDK `CallToolResult` with `isError: true`, structured content, and equivalent JSON text. Expected failures are translated at the tool boundary rather than thrown as generic SDK exceptions that lose the code. Invalid protocol messages and SDK argument-schema rejection remain SDK-owned and are not falsely advertised as domain errors; the SDK may itself use a tool-error result for schema rejection. Each advertised output schema uses JSON Schema 2020-12 anyOf to include the tool-specific success payload and the shared error payload; both structured result variants must conform. The wire isError flag distinguishes tool failures independently of that schema. SDK-generated schema-rejection results without structured content remain SDK-owned. Validate both domain variants in contract tests, even if the SDK skips output validation for isError results. Unexpected exceptions return `internal_error`, a generic message, and no traceback/body to the client.

Stable domain codes: `invalid_document`, `invalid_field`, `invalid_level`, `invalid_criterion`, `invalid_query`, `invalid_override`, `draft_not_found`, `draft_read_failed`, `draft_write_failed`, `document_too_large`, `response_too_large`, `project_not_found`, `project_mismatch`, `project_identity_unresolved`, `upstream_unavailable`, `upstream_invalid_response`, `rate_limited`, `internal_error`. Recoveries identify an actual next action, such as supplying an explicit document, fixing a field, retrying a public read later, or reading after an uncertain write. There are no revision/conflict or validation-bypass tokens.

## Nine success payloads

All rows also contain `schema_version: 1`. Input signatures are defined in [specification section 4](specification.md#4-tool-surface).

| Tool | Required result properties |
| --- | --- |
| `get_criteria` | `level: Level|null`, `levels: Level[]`, `criteria: Criterion[]`, `catalog: CatalogRef`. No level gives the six-level index and an empty criteria array. `Criterion` has `criterion_id`, `level`, `description`, `details: string|null`, `category: string|null` (upstream major group), `requirement: string|null` (upstream MUST/SHOULD/SUGGESTED category), `status_field`, `justification_field`, `aliases: string[]`, `na_allowed: boolean`, `na_justification_required: boolean`, `met_justification_required: boolean`, `met_url_required: boolean`, `source_url`. Official text is retained, not rewritten by a model. |
| `find_project` | `query: string`, `query_kind: "id"|"url"|"text"`, `page: integer`, `candidates: Candidate[]`, `next_page: integer|null`, `pagination_complete: boolean`, `observation: {source_url, fetched_at}`. `Candidate` contains `project: Project`, `match_basis: "id"|"repo_url"|"homepage_url"|"url_query"|"text"`. |
| `get_project_progress` | `project: Project`, `level: Level|null`, `summaries: Summary[]`, `answers: Draft`, `criteria: SavedCriterion[]`, `observation: Observation`, `catalog: CatalogRef`, `summary_metadata: object` containing only present upstream badge_level, tiered_percentage, baseline_tiered_percentage values. `Summary` has `level`, `upstream_percentage: number|null`; no local percentage substitutes for a missing one. `SavedCriterion` has `criterion_id`, `status_present`, `status: JSON value`, `justification_present`, `justification: JSON value`; absent values use null with presence=false. No level returns summaries/metadata with empty answers/criteria. A level returns filtered supplied canonical fields, preserving unexpected upstream field values for diagnostics, never synthesizing `?`. |
| `build_draft` | `draft: Draft`, `issues: StructuralIssue[]`, `serialized_size_bytes: integer`. Only unknown-field warnings can remain after a successful mutation. |
| `read_draft` | `project_id`, `draft: Draft`, `location: string`, `issues: StructuralIssue[]`, `serialized_size_bytes: integer`, `identity: Identity`. Recognized invalid values remain visible with diagnostics. |
| `update_draft` | `project_id`, `applied_patch: object`, `created: boolean`, `location: string`, `issues: StructuralIssue[]`, `serialized_size_bytes: integer`, `identity: Identity`. Applied patch is the normalized accepted request, including null removals and content no-ops; no full document echo. |
| `validate_draft` | `project_id`, `level`, `draft_source: DraftSource`, `identity: Identity`, `catalog: CatalogRef`, `findings: Finding[]`, `checked_criteria: string[]`, `skipped_criteria: Skipped[]`. `Finding` has `criterion_id: string|null`, `field`, `code`, `requirement: string`, `message`. `Skipped` has `criterion_id`, `reason: "status_absent"|"status_unknown"|"status_invalid"|"other_level"`, `checks: string[]`. |
| `prepare_update_url` | Common artifact result below, plus `requested_overrides: string[]`, `effective_overrides: string[]`; `artifact` is `{url: string, encoded_size_bytes: integer}` or null. |
| `prepare_update_script` | Common artifact result below; `artifact` is `{javascript: string, suggested_filename: string, instructions: string, encoded_size_bytes: integer}` or null. Script byte count measures UTF-8 JavaScript source. |

`validate_draft` checks only represented selected-level criteria; wholly absent criteria appear in neither scope array. A criterion with a supplied field appears in checked scope for shape checks and may also appear in skipped scope for conditional checks; these arrays are not disjoint. Unknown fields receive `unknown_field` findings with null criterion ID. Other-level fields are outside checks and receive skipped scope entries, not selected-level invalidity findings. Metadata shape checks use null criterion ID. Supported finding codes are `invalid_type`, `invalid_status`, `unknown_field`, `na_not_allowed`, `missing_required_justification`, `missing_required_url`. Invalid statuses skip conditional checks. `Unmet` has no conditional evidence requirement. The exact five-character/comment-prefix/URL predicates remain those in spec section 4.

The populated criterion booleans express upstream requirements, including implied requirements. Upstream deliberately permits omitting an entailed YAML field: `met_url_required` implies `met_justification_required`, and `na_justification_required` implies `na_allowed`. Catalog generation expands those implications before publishing explicit values; omission of an entailed field is not absence of the requirement. The original YAML and raw independent source oracle remain unchanged as provenance. For example, gold `build_reproducible` publishes both Met flags as true. These are mechanical upstream conventions, not host policy or predictions about saved form values.

For a Met answer requiring a URL, validation reports `missing_required_url` without also reporting the entailed `missing_required_justification`. A matching URL satisfies both existing predicates. This follows upstream's stronger-first checks and retains the accepted answer set; standalone justification and N/A checks retain their existing predicates.

## Identity and source decisions

Check a present `id` as a strict positive integer equal to the requested target. Wrong type is `project_identity_unresolved`; a different valid ID is `project_mismatch`. For stored reads/updates, check source identity before patching; a patch cannot silently repurpose another project's file. Recovery is explicit host/user repair of the misplaced file, or a corrected explicit document for document mode. `build_draft` has no target and only preserves/removes provenance. Validation with explicit/stored input checks `id` but does not check `repo_url` against the network (`repo_check: "not_checked"`).

Generators check any supplied `repo_url` against the fetched project. Both URLs must be absolute HTTP(S), have a host, and contain no credentials. Compare after lowercasing scheme/host and removing the scheme's default port; preserve scheme differences, path case, trailing slash, query, fragment, and percent encoding. Do not drop `.git`, follow redirects, fetch the URL, or equate providers. Identical normalized values match. Different comparable values are `project_mismatch`; missing/unusable upstream provenance when a draft URL is supplied is `project_identity_unresolved`. Both prevent artifacts. Absent draft provenance is allowed and honestly reported as explicit targeting or storage association. No additional host registration state is stored.

## Transfer report and aggregation

Common artifact result: `project_id`, `level`, `catalog`, `draft_source`, `observation`, `identity`, `outcome`, `artifact`, `no_artifact_reason: string|null`, `transfer: TransferField[]`. One row per supplied normalized field, including provenance and fields outside the level. `TransferField` contains `field`, `disposition: "encoded"|"unchanged"|"outside_level"|"unsupported"|"invalid"|"omitted"`, `reason: string`, `expected_application: "fill"|"replace"|"retain_existing"|"blocked_by_status"|"unchanged"|"not_applicable"|"unknown"`, `override: boolean`. Do not repeat answer bodies in the report. An encoded field is a proposal, not a saved update. `expected_application` describes edit-form behavior against the public observation; it does not predict Save/Submit acceptance or final persisted values. Unknown saved values use expected_application=unknown. Missing statuses are not assumed blank; omitted known justifications in a complete valid pinned public record have the specific blank interpretation documented in the [upstream baseline](upstream-compatibility.md). This never synthesizes progress answers or document fields.

Classify in this order after upstream precedence and override coupling:

1. Any encoded fields plus any requested unsupported/invalid/omitted fields yields `partial`.
2. Any encoded fields with none of those omissions yields `complete`, even if upstream is predicted to retain existing values. The report shows the ineffective replacements.
3. No encoded fields and any unsupported/invalid/omitted requested fields yields `no_transferable_changes` and artifact=null.
4. Otherwise, any meaningful in-scope fields identical to saved values yields `no_changes` and artifact=null.
5. Otherwise, `no_supplied_transferable_answers` and artifact=null (empty document, provenance-only, or other-level-only).

Unknown fields are unsupported; provenance rows are omitted with reason `provenance_not_editable` and excluded from requested-work aggregation. Other-level fields are also excluded from aggregation. Status `?` is unsupported (`unknown_status_not_transferred`) and counts as unrepresented work even when matching a saved `?`; its valid supplied justification is evaluated independently. An invalid in-scope status or unsupported `N/A` is not equivalent to `?`: omit its accompanying supplied justification with `invalid_companion_status`. A justification of invalid type does not disqualify an otherwise valid supplied status. No missing justification or evidence-URL check runs during generation.

Invalid shape/value of recognized fields outside the selected level does not stop generation; report outside_level. Metadata is in scope for each supported edit form. Structurally unreadable documents still fail the whole call. Null input field values are invalid for recognized draft fields, not deletion requests; only patch null removes locally.

Predict URL application with the pinned upstream whitespace normalization documented in the baseline; preserve raw draft/encoded text. For URLs, encode valid differing unforced proposals even when predicted to remain divergent. Never prune a differing known status to evade its block on the supplied justification. Preserve effective justification overrides inherited from an unchanged status before pruning that status. Requested overrides are deduplicated exact canonical fields, supplied and writable in scope; reject aliases, globs, unknown/provenance/out-of-scope/unsupplied entries. Report requested overrides even if their fields are unchanged or nontransferable; effective overrides are those actually encoded, including inherited justification overrides. Scripts use replacement semantics and accept no overrides.

No-artifact reason equals the outcome enum, accompanied by field reasons in the transfer report. A valid empty search, completed validation with findings, and null artifact all remain successful tool results. Scripts share the null-artifact classifier; do not emit empty executable scripts merely to satisfy a return type.

## Resource and network policy

These are server resource limits, not BadgeApp field or URL transport limits. Initial constants are 1,048,576 bytes per normalized draft or patch, 16,777,216 bytes per serialized SDK tool-result object (including structured and compatibility text representations), and 8,388,608 decompressed bytes per upstream response. Draft/file input is additionally bounded at 1,048,576 raw UTF-8 bytes before parsing. Maximum JSON nesting is 64. Serialization for draft size and file bytes uses UTF-8, ensure_ascii=false, sorted keys, compact separators, no non-finite values, and one final newline. Tool-result measurement uses the pinned SDK's actual wire serialization, excluding the JSON-RPC ID/frame. A host may impose a smaller limit; qualify it at release rather than claiming universal capacity.

Before replacement, serialize both the candidate document and the complete prospective read result, including diagnostics, absolute location, identity, and text fallback; require both budgets to pass. A no-op update also performs these checks. Incoming oversized stored/imported files fail explicitly; they are never truncated. Large criteria/progress/search results fail `response_too_large` with filter/page guidance. An artifact that exceeds the response budget fails explicitly, not with a partial URL or guessed URL-length threshold. Boundary fixtures must include Unicode, escaping, unknown-field diagnostics, and long storage paths; exact envelope accounting is required even with generous headroom.

Use one lifespan-managed asynchronous HTTP client, no cookies/authentication, fixed production origin, and a descriptive User-Agent containing package/version. Do not follow redirects; return `upstream_invalid_response` for unexpected redirect or HTML login/error content. Never fetch candidate/evidence/repository URLs. Send only documented query parameters. Share a monotonic limiter across all calls/retries: at most one request start per second per process. No cache of project observations across calls.

Each read has at most three attempts and a 30-second overall deadline, including limiter wait, backoff, and body reads. Each attempt has a 10-second timeout, with connection timeout at most 5 seconds. Retry only transient connection/read failures and HTTP 429/502/503/504; delays after attempts one/two are at least 1/2 seconds, also subject to pacing. Parse Retry-After as nonnegative seconds or HTTP date; apply its delay as a shared cooldown. If the cooldown exceeds the remaining deadline, return immediately with rate_limited and retry_after_seconds rather than sleeping past the budget. Never shorten a valid cooldown; malformed values use normal backoff. HTTP 404 maps to project_not_found on a single-project read and empty candidates for ID discovery; other unexpected HTTP/schema failures do not retry. Cancellation stops pending reads/waits and releases resources. HTTP errors do not expose response bodies.

## Storage and protocol adaptation

Resolve defaults without creating them: macOS `~/Library/Application Support/bestpractices-mcp`; Linux `$XDG_DATA_HOME/bestpractices-mcp` when absolute, otherwise `~/.local/share/bestpractices-mcp`; Windows `%LOCALAPPDATA%/bestpractices-mcp`. Empty/relative BESTPRACTICES_DATA_DIR is startup configuration error. An existing override must be a directory; missing absolute roots are allowed. Do not expand `~` in an override. Reject symlinks in server-managed `projects`, project directory, and draft destination, and non-regular draft files. Resolve the configured root once; a user-chosen root may itself resolve through a symlink. Protect against accidental path escape; hostile concurrent replacement of ancestor directories by another local user is outside the single-writer local-storage guarantee.

Use a process-local per-project async guard, a same-directory temporary file, owner-only creation permissions where supported, preserved destination permissions, flush plus file fsync, then atomic replacement. Clean temporary files on handled pre-replacement failure; cancellation must not strand a held guard. Shield the bounded replace/cleanup critical section so cancellation cannot trigger a retry of a possibly committed write. Atomic visibility is promised; survival of sudden hardware/power failure is not. Never claim rollback after replacement. Empty directories left by a failed first update may remain; no successful draft is claimed.

Use SDK annotations: readOnlyHint=true for all but update_draft; update_draft has readOnlyHint=false and destructiveHint=true because it can replace/remove local fields. idempotentHint=true for deterministic local document/catalog operations and update_draft's content semantics; document that this does not authorize retries after ambiguous writes. Public reads/generators are read-only but time-dependent. openWorldHint=true only for network tools. Discovery/list caching uses SDK CacheHint(ttl_ms=0, scope="public"); no application-result caching is promised. Keep handlers small; services return domain objects and the MCP boundary performs schema/error/size adaptation.

## Required contract examples

Regression fixtures cover these cases.

- `build_draft({},{"description_good_status":"Met"})` returns that single-field document; optional validation may find a missing explanation, while generation still proposes Met.
- `build_draft({"extra":{"x":1}}, {})` preserves extra with unknown_field diagnostic; setting extra non-null fails; removing extra with null succeeds.
- `read_draft(123)` missing returns draft_not_found and creates nothing. `update_draft(123,{})` creates an empty draft. A repeated empty update has created=false.
- `validate_draft(123,"passing",{})` checks no criteria and performs no file or network access. `draft:null` fails argument validation.
- An omitted draft loads the stored file; explicit `{}` ignores even a malformed stored file. A mismatched stored id fails read/update before mutation.
- Saved Met with old justification, supplied Met with new justification, and override on the status encodes the changed justification with its effective override even though the status is unchanged.
- Saved Unmet, supplied Met plus text, only the justification overridden: the URL preserves the proposed status, reports retain_existing and blocked_by_status, and does not predict replacement.
- Unknown-only input yields no_transferable_changes; other-level-only input yields no_supplied_transferable_answers; matching supplied fields yield no_changes; matching plus unsupported work yields no_transferable_changes.
- A script on the wrong origin/project/level or missing intended control makes zero changes. Direct assignment/dispatch failures produce runtime_failed with completed fields; browser event-listener exceptions may remain browser-reported and cannot be certified by that result. Neither result implies atomic rollback or a saved update.
